# ACE3, FULLY SCOPED — what it is, and what of it we are building ourselves

_UI specialist, 2026-08-24, at Battlewrath's direction: *"It might be we need to reframe. Fully scope
ace and see what it saves us from developing."* Sources he gave: the Wowpedia Ace page and
`github.com/WoWUIDev/Ace3`. **This file rules nothing.** §3 is the basis; §4 is a READ, marked as
mine. Companion to `prior_art_ace_field_2026-08-21.md`, which surveyed how the FIELD uses Ace; this
one asks what Ace CONTAINS and what we would not have to write._

---

## 1. What Ace3 says it is

> *"a comprehensive framework for WoW AddOn development to streamline many of the common tasks"* —
> the Ace3 repository description, `github.com/WoWUIDev/Ace3`

And Wowpedia's philosophy line: **"less is more"** — less code, fewer resources, less effort, less
stress on the UI.

⚠⚠ **NEITHER SOURCE MENTIONS LAYOUT, RESOLUTION OR SCALE.** Wowpedia's component list is Ace2's
(AceLibrary · AceOO · AceAddon · AceComm · AceConsole · AceTab · AceDB · AceEvent · AceDebug ·
AceHook · AceLocale · AceModuleCore) and notes only in passing that *"The current version is Ace3"*.
⟶ The advertised draw is **plumbing**, not layout. ★ This corrects a read this seat made on
2026-08-23 — that resolution-independence is "very plausibly why people use Ace". It is a real
property (§2) but it is a CONSEQUENCE, not a claim Ace makes.

## 2. The one thing Ace does with resolution: nothing

Counted across `AceGUI-3.0/` and `AceConfig-3.0/`, every file, our shipped copy:

    resolution = 0    aspect = 0    GetScreenWidth = 0    GetEffectiveScale = 0    SetScale = 0

Instead: **a width UNIT** (`AceConfigDialog-3.0.lua:83` `local width_multiplier = 170`; `:1219-1225`
`"double"` ×2, `"half"` ÷2), and **Flow wraps on the CONTAINER** (`AceGUI-3.0.lua:687` takes
`content.width or content:GetWidth()`, `:726` breaks the row when `usedwidth > width`). Nothing in
that chain is a screen dimension, so changing resolution, aspect or UI scale changes no arithmetic.
⚠ Counted on **r33**; §580 established r41 differs on every widget checked.

## ★ RESOLVED SAME DAY — read §4 against `AL-46`, not as an open question
Battlewrath ruled the posture (`ARCHITECT_LOG.md` AL-46): **YES, scoped.** For the plumbing —
comm · serialisation · DB · lifecycle · events · timers · hooks · console — the default is USE, a
hand-rolled equivalent owes a written reason, and adoption happens **ON TOUCH, never as a migration
sprint.** It does **not** extend to the layout/offline domain: frame model, panespec, coordinate
space, driver, route contract are the PRODUCT, not custom code on trial. His why:

> *"Our ability to code is not limited. Knowing what form the code needs to take to operate in WoW
> has just been handed to us whole sale."*

⚠⚠ **AND §4'S LEAST-SURE ROW WAS SETTLED BY A CAPABILITY FACT, NOT THE MEASUREMENT I ASKED FOR.**
I wrote that the AceBucket question was *"does Ace's have our latency budget"* and that nobody had
measured it. The architect's `ace3_gap_2026-08-24.md` §1 makes the measurement **moot**: AceBucket's
aggregation keeps **only arg1 as a table key with an occurrence count; every other argument is
dropped.** Our coalescing carries multi-arg readings, so a lossy one-key bucket cannot hold them at
any latency. ⟶ **REJECT for the hot path**, and ours is residue with its reason written.
★ The lesson for this seat: I framed a capability question as a performance one, and a performance
question is the more expensive kind to answer.

★★ **AND THREE THINGS COME BACK TO THIS LANE AS BORROWS** (gap §1, `AceConfig` row): the **width
unit** (170 base, half/double/relative — resolution-independence with zero screen reads), the
**validate → error / confirm → popup** shape, and **NotifyChange** (one notification, open surfaces
re-fetch and redraw). Ideas into `panespec`, cited — not an adoption.

## 4. THE READ — marked as the UI specialist's, not a ruling

**★★★ THE ONE THAT LOOKS LIKE PURE SAVING: `AceBucket-3.0`.** Our `bucket.lua` is 91 matches of the
job AceBucket names in one line of its own description, and `manager.lua` another 61. ⚠ **But this
is the row I am least sure of**, and deliberately so: `debuglog.md` and the mancer stutter work say
our coalescing exists to serve a MEASURED hot path, and a library's bucket is a general one. **The
question to ask is not "does Ace have this" but "does Ace's have our latency budget".**

**★★ THE ONE THAT IS OWED ANYWAY: `AceSerializer-3.0` + `AceComm-3.0`.** AceComm is the only row
where we hand-roll **nothing** — and AP-8..AP-12 put route sharing on the road. So this is not
"replace what we built", it is **"do not build it"**: chunking, reassembly and a wire format are
exactly the tedious, already-solved half, and `travelling-data-NAMES-never-supplies` is a rule about
what we put IN the payload, not about who moves it.

**★ THE ONE THE FIELD SAYS WE ARE ALONE ON: `AceDB-3.0`.** `prior_art_ace_field` §6b: we are the only
Ace3-embedding addon of 21 with **zero AceDB**; the other 20 carry it (minors 15–27) and 20 carry
LibDualSpec. And §1 above reframes that — if the framework's advertised purpose IS the plumbing,
then we have taken the widget half and left the half Ace is *for*.

**⚠ THE ONE THAT IS NOT A SAVING: `AceGUI-3.0` / `AceConfig`.** We already embed AceGUI and already
build panes against it. The 21 `CreateFrame` in `object.lua` are not a missing library — they are
`panespec`'s deliberate zones→rows→cells, which is offline-checkable in a way an option table is not
(`ui_overhaul_scope.md` defends `hidden` as a static subject set for exactly that reason). ★ The open
question there is the one §6a already filed: **we ship 13 of the 17 widget types AceConfigDialog
constructs, and `ScrollFrame` is missing and load-bearing.**

## 5. WHAT THIS DOES NOT ESTABLISH
- Whether any adoption is worth its cost. Every row above is a fact about code that exists; none is
  a migration estimate, and none accounts for the hot path.
- The r41/r33 gap (§580): counted on **r33**, and which copy runs is decided by LOAD ORDER on this
  fork, not version, because every Ace minor reads `1.#INF`.
- `AceTimer-3.0` minor **1017** is anomalous against every other minor here and is not explained.
